# Architecture Decision Log

Short ADRs for every non-obvious choice. Format: context, decision, consequences.

---

## ADR-001: Shared-schema multi-tenancy with a `tenant_id` column

**Context.** Small businesses, many tenants, low data volume each. Options: database per tenant, schema per tenant, shared schema.

**Decision.** One schema; every tenant-owned table has `tenant_id NOT NULL` with an index. The tenant comes from the URL (`/api/t/{slug}/...`, `/api/public/tenants/{slug}/...`). `TenantResolutionFilter` resolves it after authentication and binds a `TenantContext` (tenant id, zone, caller membership and role) for the request.

**Consequences.** Cheap to run and migrate (one Flyway history). Isolation depends on discipline, so it is enforced in three layers (ADR-002) and tested on every tenant-scoped endpoint (`TenantIsolationIT`).

## ADR-002: Defence in depth for tenant isolation

**Decision.**
1. **Explicit queries.** Every repository lookup takes the tenant id (`findByIdAndTenantId`, `search(tenantId, ...)`).
2. **Hibernate `@Filter`.** `TenantFilterAspect` enables `tenantFilter` on the session before any repository call while a tenant context is bound. This also guards JPQL and collection loads that a developer forgets to scope.
3. **Service-level authorization.** `TenantAccess.requireMember()/requireOwner()`.

Hibernate filters do not apply to `EntityManager.find` (`findById`), which is why layer 1 exists and `findById` is never used for tenant-owned data in tenant context.

**Consequences.** A wrong id in tenant A's URL is simply "not found".

## ADR-003: 404 (not 403) for non-members; 403 for insufficient role

**Decision.** Not a member of the tenant → 404, so tenant-private resources do not reveal they exist. A member whose role is too low (STAFF on an OWNER action) → 403. Customers who are not members get 404 on management endpoints and on other customers' bookings.

**Consequences.** The frontend shows "no access" based on `/api/me` memberships rather than relying on 403s.

## ADR-004: ThreadLocal `TenantContext` instead of a `@RequestScope` bean

**Context.** The spec asks for a request-scoped tenant context.

**Decision.** A record held in a `ThreadLocal` that the filter sets and always clears in `finally`. Lifetime is exactly the request. It works in filters (before `RequestContextFilter` scopes exist) and in plain unit tests, and it fails loudly (`IllegalStateException`) if read outside a request.

## ADR-005: Double booking is prevented by the database, not just the code

**Decision.**
1. The server re-runs the slot engine for the requested start (never trusts the client).
2. A PostgreSQL exclusion constraint (`btree_gist`) rejects overlapping `PENDING_PAYMENT`/`CONFIRMED` bookings per staff member.
3. `@Version` optimistic locking guards concurrent status changes on one booking.

When two transactions race, PostgreSQL makes the loser fail with **23P01** (exclusion violation) or, when both checks wait on each other, **40P01** (deadlock). Both are translated to `409 Slot no longer available`. `BookingConcurrencyIT` fires 10 parallel requests and asserts exactly 1×201 and 9×409.

**Consequences.** Correct under any number of app instances, with no distributed lock.

## ADR-006: `ends_at` includes the service buffer

**Decision.** `booking.ends_at = starts_at + duration + buffer`, the interval the staff member is blocked. The API's `endsAt` field is the end of the service itself (`startsAt + duration`).

**Consequences.** The exclusion constraint protects clean-up time too, and the slot engine treats bookings as plain busy intervals.

## ADR-007: Slot engine is a pure function

**Decision.** `SlotEngine.availableStarts(SlotQuery)` takes the date, zone, working ranges, busy intervals, duration, buffer, earliest start and step, and returns `ZonedDateTime`s. `AvailabilityService` does the I/O in a fixed number of queries (staff links, members, hours, blackouts, bookings).

Candidates are generated by walking the **local** clock in 15-minute steps and converting each to an instant with `ZonedDateTime.of`. On a DST spring-forward day, nonexistent local times collapse onto real ones and are de-duplicated. Manila has no DST, but the engine is tested with `America/New_York` anyway.

**Consequences.** 17 unit tests run in milliseconds; no mocking needed.

## ADR-008: Rotating opaque refresh tokens with family revocation

**Decision.** 256-bit random tokens, stored as SHA-256 hashes, 7-day expiry. Each refresh revokes the presented token (`revoked_at`, `replaced_by`) and issues a successor with the same `family_id`. Presenting a revoked token is treated as theft: the whole family is revoked and the user must sign in again. The token row is read `FOR UPDATE` so two simultaneous refreshes cannot both succeed. Logout revokes the family.

**Deviation.** The spec's `refresh_token` table gained a `family_id` column; without it, family revocation needs a recursive walk of `replaced_by`.

**Note.** `RefreshTokenService.rotate` is `noRollbackFor = UnauthorizedException` so the family revocation commits even though the request fails.

## ADR-009: Roles are not in the JWT

**Decision.** Access tokens (HS256, 15 minutes) carry only `sub` and `email`. Roles are resolved per tenant from `membership` on every request.

**Consequences.** Removing a staff member takes effect immediately, at the cost of one indexed lookup per tenant-scoped request.

## ADR-010: Frontend token storage

**Decision.** Access token in memory; refresh token in `localStorage`. The API client refreshes on 401 once, shares a single in-flight refresh between concurrent requests, and makes requests issued during a refresh wait for it, so a rotating token is never presented twice (which would trigger ADR-008's theft detection).

**Trade-off.** An `HttpOnly; SameSite` cookie would resist XSS better, but the target deployment puts the frontend (Vercel) and API (Render) on different sites, which makes third-party cookies unreliable. Mitigations: short access-token lifetime, reuse detection, CSP on the API, no `dangerouslySetInnerHTML`.

## ADR-011: Webhook idempotency in the same transaction as the state change

**Decision.** `INSERT ... ON CONFLICT (event_id) DO NOTHING` into `webhook_event`, then apply the event and set `processed_at`, all in one transaction. A duplicate returns `DUPLICATE` (200). If processing fails, the insert rolls back too and PayMongo's retry is processed normally. A concurrent duplicate blocks on the unique index until the first transaction finishes, then becomes a no-op.

Signatures: `Paymongo-Signature: t=..,te=..,li=..`, HMAC-SHA256 over `t + "." + rawBody`, compared in constant time, with a 5-minute timestamp tolerance against replay.

## ADR-012: Money as `BIGINT` centavos, time as `TIMESTAMPTZ` in UTC

**Decision.** All amounts are integer centavos (`long`). Deposits are computed with `BigDecimal` and rounded half-up. Timestamps are `timestamptz`; Hibernate uses `jdbc.time_zone=UTC`. Responses convert to the tenant's zone (`OffsetDateTime` with `+08:00`). Analytics group by `starts_at AT TIME ZONE :tz` so "per day" means the business's day.

## ADR-013: Notifications after commit, asynchronously, idempotently

**Decision.** Services publish `BookingNotificationEvent`; `BookingNotificationListener` is `@Async` + `@TransactionalEventListener(AFTER_COMMIT)`. `NotificationService.sendBookingEmail` runs in `REQUIRES_NEW`, skips if a `SENT` row exists, and a partial unique index `(booking_id, type, channel) WHERE status='SENT'` makes duplicates impossible. Failures are logged as `FAILED` and retried by the next reminder run. The reminder loop lives in `ReminderJob` (not in the service) so each send goes through the transactional proxy.

`NotificationSender` has an `EmailNotificationSender` (Spring Mail + Thymeleaf) and a logging `SmsNotificationSender` to show where a real SMS provider would plug in.

## ADR-014: Checkstyle configuration

**Decision.** Derived from checkstyle's `google_checks.xml` (2-space indent, import, naming, whitespace and brace rules) with line length 120 and **Javadoc rules removed**: the codebase favours expressive names, with docs where behaviour is non-obvious. The build fails on any violation.

## ADR-015: JaCoCo gate on `*Service` classes

**Decision.** `jacoco:check` aggregates line coverage over every class named `*Service` and fails under 70%. Integration and unit tests both run under Surefire (`*Test`, `*IT`) so one report covers them. Current: about 96% service-layer and 82% overall line coverage.

## ADR-016: Integration tests share one container and one context

**Decision.** A singleton `PostgreSQLContainer` (`postgres:16-alpine`) with `@ServiceConnection`, a single cached Spring context (the mocks live in the base class), and `TRUNCATE ... CASCADE` before each test. Only the outermost boundaries are mocked: `JavaMailSender` and `PaymentGateway`. Schema validation (`ddl-auto=validate`) runs against the real Flyway schema, never `create`.

Testcontainers is pinned to 1.21.4: earlier versions use Docker API 1.32, which Docker Engine 29 rejects.

## ADR-017: Soft deletes for services and staff

**Decision.** `DELETE /services/{id}` hides the service (`active=false`); `DELETE /staff/{id}` deactivates the membership. Bookings and the audit trail keep pointing at them. The last active owner cannot be demoted or removed (409).

## ADR-018: Queue ticket numbers and positions

**Decision.** Ticket numbers come from `queue_counter (tenant_id, queue_date)` via one atomic upsert (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`), so they restart every tenant-local day with no gaps or duplicates. "Call next" claims the lowest waiting ticket with `FOR UPDATE SKIP LOCKED`, so two staff pressing it together get different customers.

**Deviation.** The spec lists a stored `position` column; position is derived on read (rank among `WAITING` tickets) because a stored value goes stale on every call, skip and serve. A `queue_date` column was added for the per-day numbering.

## ADR-019: STOMP topic pushes the whole public queue

**Decision.** After each queue change commits, `QueueBroadcaster` sends the full public state (ticket numbers, statuses, positions, never names or phones) to `/topic/tenants/{slug}/queue`. Clients replace their state wholesale, so missed messages self-heal on the next one. Topics carry only public data, so subscriptions need no authentication.

## ADR-020: Payments without keys

**Decision.** If `PAYMONGO_SECRET_KEY` is empty, `payment-intent` returns 503 "Online payments are not configured", and deposit bookings stay `PENDING_PAYMENT` until the expiry job releases them after 15 minutes. No simulated payment endpoint exists, so there is nothing that could be abused in production. The demo's main tenant (Kanto Cuts) needs no deposit.

## ADR-021: `DATABASE_URL` accepts JDBC or libpq URLs

**Decision.** `DatabaseUrlEnvironmentPostProcessor` converts `postgres://user:pass@host:port/db` (what Render provides) into `spring.datasource.*`. JDBC URLs pass through untouched.

## ADR-022: Rate limiting is in memory and per instance

**Decision.** Bucket4j buckets keyed by `remoteAddr + path` for `POST /api/auth/login` and `/register`, 5 per minute, answering 429 with `Retry-After`. Idle buckets are evicted every 10 minutes. `server.forward-headers-strategy=framework` makes `remoteAddr` the real client behind Render's proxy.

**Consequences.** Limits are per instance. Scaling out would need Bucket4j's Redis/JDBC backend.

## ADR-023: Additional packages beyond the suggested layout

`audit/` (audit log entity, service, controller) and `seed/` (demo data) were added as their own feature packages rather than squeezed into `analytics/` or `config/`.

## ADR-024: Seed data

**Decision.** A `@ConditionalOnProperty(queueup.seed-demo=true)` `ApplicationRunner`, idempotent (skips if `kanto-cuts` exists), deterministic (fixed `Random` seed). History is inserted with a JDBC batch (about 1,100 bookings in under a second); upcoming bookings are generated by walking each staff member's day, so they never violate the exclusion constraint.

## ADR-025: Frontend structure

React Router routes with lazy-loaded dashboard pages (Recharts lives in its own chunk), TanStack Query for server state, React Hook Form + Zod for forms, and a tiny toast context instead of a UI library. Booking-flow state lives in the URL, so it survives the sign-in redirect and the back button works. Dates in the picker are `YYYY-MM-DD` strings, and all formatting uses `Intl` with the tenant's `timeZone`, so the browser's own zone never leaks in.
